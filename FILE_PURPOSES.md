# FILE_PURPOSES.md

Every tracked file in this repository and what it is for. Read it when you are
unfamiliar with a subsystem, need to know which file owns a responsibility
before editing, or are planning a change that spans modules.

**Tracked means `git ls-files`.** Build output (`js/dist/`, `js/python/`,
`python/build/`), dependencies (`node_modules/`, `python/.venv/`), caches and
generated files like `captchakraken.env` are gitignored and get no entry, ever.
Add or delete a tracked file and this list changes in the same commit.

This file answers "where does X live?". Its companion answers "does a helper for
this already exist?": `repomix-output.md`, a comment-stripped signature map of
all three ports, regenerated by `npm run repomix` in under a second. It is
gitignored on purpose — a generated map that is committed goes stale and still
gets trusted — so grep it, and if it is missing, rebuild it.

There is no database in this repository. The client is stateless per solve; the
only state it keeps is on the caller's own disk (`~/.captchakraken/`: the
credentials file, a pidfile and a server log).

## How it fits together

Three published artifacts come out of one repo:

| Artifact | Registry | Source | Ships |
|---|---|---|---|
| **captchakraken** | npm | `js/` | The browser driver, plus a copy of the Python engine |
| **captchakraken** | PyPI | `python/` | The engine, the page driver and the CLI |
| **captchakraken-mcp** | npm | `mcp/` | Account sign-in and API-key management |

The flow of one solve, whichever port you start from:

```
your Page  ──>  driver (js/src/solver.ts  or  python/.../page_solver.py)
                  │  screenshot the widget
                  ├─>  find_grid (CPU detector) ──> overlay.py draws cell numbers
                  ├─>  planner.py ──> HTTP ──> vLLM endpoint (local or hosted)
                  │                             prompts.py picks the generation
                  │                             models.json says which, per model
                  ├─<  an action plan (action_types.py)
                  ├─>  humanize.py performs it as mouse or touch
                  └─>  verify, or go round again
```

The TypeScript driver owns no inference of its own: it shells out to the bundled
Python CLI (`js/src/cli-invocation.ts` → `python/src/captchakraken/cli.py`), so
grid detection and prompting have exactly one implementation. The two ports are
otherwise mirrors of each other, and `contract.json` is what holds them level.

Animated challenges take one extra stage: the driver records a burst,
`keyframes.py` cuts it down to the frames the model is shown, and the model
answers with a frame number the driver then waits for on screen.
